# Decisioni di progetto

| Data | Decisione | Alternative valutate | Motivo |
|---|---|---|---|
| 26/10/2026 | Impresa: tarallificio B2B fittizio "GemmaTaralli" | fornitore di servizi IT B2B per PMI, software house verticale (per esempio un gestionale SaaS per attività sportive), produttore di macchine confezionatrici | ho scelto questa impresa perché più coerente con il tema di digitalizzazione d'impresa e perché la tracciabilità del lotto di produzione dà vita a scenari concreti |
| 26/10/2026 | Interfaccia web + runner headless per i test | solo CLI | la web permette di mostrare tutti i passi del ciclo e la chat con l'agente, mentre il runner ripete gli scenari su più LLM |
| 26/10/2026 | Linguaggio Python | TypeScript o C# | SDK MCP ufficiale in Python disponibile, conoscenza pregressa acquisita da lavoro |
| 26/10/2026 | DB SQLite | PostgreSQL | non necessario poiché non è un'app necessariamente scalabile, un singolo file va benissimo |
| 26/10/2026 | SDK Python ufficiale MCP (pacchetto mcp), trasporto stdio | librerie MCP di terze parti | l'SDK ufficiale è richiesto dalla traccia; stdio è il trasporto più semplice con server e client che girano sulla stessa macchina |
| 26/10/2026 | Ciclo agentico scritto a mano | LangChain, LangGraph, CrewAI, AutoGen | vietati dalla traccia; il ciclo agentico scritto a mano permette un controllo completo su errori, conferme, arresti e log |
| 26/10/2026 | Tenere conferma separata dall'interfaccia | conferma gestita dentro la web | lo stesso ciclo funziona con la web interface e con il runner dei test |
| 27/10/2026 | Modelli locali: qwen3:8b (principale), gemma4:e4b (confronto) | qwen3:14b, llama3.1:8b (troppo datato), Llama 4 Scout scartati poiché non entrano in memoria (Llama 4 Scout) oppure troppo lenti con offload su CPU (qwen3:14b) | entrano negli 8 GB di VRAM della mia RTX 2070 e supportano il tool calling, LLM più grandi con troppi parametri sarebbero troppo lenti |
| 27/10/2026 | Nessun tool per il richiamo di un lotto | richiamo gestito dall'agente con conferma | senza il tool un errore di modello o una prompt injection non può avviare un richiamo di lotto, un richiamo sbagliato danneggerebbe clienti e profitti aziendali |
| 28/10/2026 | Ho scelto la relazione tra entità ticket-attività uno a molti (1:N) | relazione molti a molti (N:M) con tabella associativa | facilitazione nella creazione dello schema e futuro tool registra_attivita semplificato; se una telefonata di un cliente tocca due reclami si registrano due attività diverse, non solo una |
| 28/10/2026 | Ho scelto la relazione spedizione-lotto molti a molti (N:M) | un singolo lotto per spedizione | una spedizione può contenere più lotti e uno stesso lotto può andare anche a più di un cliente |
| 28/10/2026 | Il lotto può essere facoltativo nel ticket (0,1) | lotto obbligatorio per ogni ticket | i reclami per ritardo e la richiesta di documentazione non riguardano necessariamente un lotto |
| 29/10/2026 | Ho scelto di collegare i ticket facoltativamente alla spedizione (0,1) | riferimento alla consegna solo nella descrizione del ticket | ritardi e danni possono riguardare una consegna precisa; facendo così, il collegamento permette di cercare i reclami anche per numero di spedizione |
| 29/10/2026 | Ruolo contatto come elenco chiuso | ruolo come testo libero | lasciare il testo libero avrebbe potuto produrre varianti che l'agente non riconosce |
| 29/10/2026 | Ragione sociale del cliente univoca | ragione sociale non univoca | evita il problema dei clienti omonimi |
| 29/10/2026 | Data scadenza salvata nel lotto | solo shelf life | ridondanza voluta poiché permette di mantenere la scadenza originali dei lotti nel caso la shelf life cambi|
| 29/10/2026 | Rinominato GT-HO1K in GT-HO001 | GT-HO100, ma si confonde con 100gr | diventa coerente con la scelta nel dizionario dati |
| 29/10/2026 | Ho deciso di aggiungere 3 check sull'entità ticket: la data di chiusura non può precedere quella di apertura; lo stato è "chiuso" solo se c'è la data di chiusura; la categoria c'è solo nei reclami | nessun vincolo nello schema, controlli solo nel codice | il database rifiuta i dati incoerenti anche se il seed o un tool sbagliano |
| 29/10/2026 | Ho deciso di garantire due vincoli nel codice invece che nello schema ovvero almeno un lotto per ogni spedizione (seed) e coerenza tra cliente, spedizione e lotto del ticket | trigger SQL | un check controlla solo la riga che si sta inserendo mentre questi vincoli richiedono di consultare altre tabelle; i trigger complicherebbero lo schema senza un vero vantaggio |
| 29/10/2026 | Categoria obbligatoria per i reclami | categoria facoltativa | oggi i reclami sono spesso incompleti; le cinque categorie coprono tutti i reclami tipici e se manca, l'agente deve chiederla invece di inventarla |
| 30/10/2026 | Dati di prova ridotti rispetto alla scheda impresa: 14 clienti 30 lotti e 16 spedizioni invece dei volumi specificati in scheda impresa | generare tutti i dati della scheda (circa 180 clienti e 60 lotti al mese) | con pochi dati verificare a mano le risposte dell'agente risulta meno complesso, è sufficente per coprire tutti gli scenari di test |
| 30/10/2026 | Dati degli scenari di test scritti a mano nel seed con seme fisso e db ricreato a ogni avvio | dati generati in modo casuale con la libreria Faker | i test devono partire sempre dagli stessi dati, così i risultati sono ripetibili e il confronto tra modelli è equo; Faker avrebbe aggiunto una dipendenza esterna senza un vero vantaggio con pochi dati e reso seed.py più complesso per via del doppio seme (random.seed e Faker.seed) |
| 31/10/2026 | Errori del data layer con raise ValueError | restituire None o una stringa | il server MCP passa l'errore al modello come errore del tool |
| 31/10/2026 | Stato e date di ticket e attività decisi dal codice | farli scegliere al modello | il modello non può inventare date o aprire ticket già chiusi |
| 31/10/2026 | aggiorna_opportunita restituisce anche lo stato precedente | solo lo stato nuovo | serve per mostrare il prima e dopo nella conferma |
